# GoodMorNing 보안 설계와 적용 기록

최종 갱신: 2026-11-27. 이 문서는 적용한 통제와 남은 위험을 구분합니다. 보안 인증이나 모든 공격에 대한 안전 보장을 뜻하지 않습니다.

## 위협 모델

사용자 사진, 쇼핑몰 HTML·상품 설명·이미지, 추천 결과는 신뢰하지 않는 외부 데이터입니다. 현재 SAM 2·YOLO는 이미지 처리, EmbeddingGemma 2는 벡터 생성/유사도 정렬에 사용하며, 자연어 지시로 SQL·셸·도구를 선택해 실행하는 LLM 에이전트가 아닙니다. 따라서 현재 방어의 중심은 외부 데이터 처리 취약점의 피해 범위 제한, 회원 자료 격리, 권한 오설정 방지입니다.

AI가 악성 지시를 알아서 거부하는 데 의존하지 않습니다. 모델 출력은 정해진 이미지·숫자 벡터·상품 필드로 취급하고, SQL 값은 파라미터로 전달하며, 상품 연결은 사용자가 선택한 결과만 저장합니다. 이후 생성형 LLM을 추가할 때도 임의 SQL/셸 실행 도구나 DB 관리자 자격 증명을 제공하면 안 됩니다.

## 적용한 DB 권한

| 연결 | 범위 | 금지 |
| --- | --- | --- |
| `goodmorning_api` | 회원 인증 테이블의 필요한 CRUD, RLS가 적용된 소유자 자료, 상품 카탈로그 읽기 | 슈퍼유저, 역할·DB·테이블 생성, 테이블 삭제/전체 비우기, RLS 우회, 상품 카탈로그 수정 |
| `goodmorning_search` | 공개 상품 카탈로그 읽기, 수집·이미지·임베딩 테이블 INSERT/UPDATE | 회원·인증·다이어리·개인 에셋 테이블 접근, 자료 삭제, 카탈로그 정식 상품/옵션 수정, DDL |
| `goodmorning_reader` | 로컬 관리자 화면에서 허용된 테이블 SELECT | 변경 명령, 인증 ID·회원 프로필·세션·OAuth 시도 테이블 조회, DDL |
| 설치/마이그레이션 관리자 | 명시적인 로컬 유지보수·백업·복원 | API/검색 서버의 기본 연결로 사용하지 않음 |

실행 역할은 `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT`로 설정하고 상위 역할 멤버십을 제거합니다. 각 역할의 비밀번호는 서로 다른 `data/postgres-api.key`, `postgres-search.key`, `postgres-reader.key`에 저장합니다. 기존 관리자 비밀번호는 `data/postgres.key`에 유지합니다. 모두 Git/배포 대상에서 제외합니다.

`server/db.py`의 실행 연결은 `GOODMORNING_API_DATABASE_URL`·`GOODMORNING_SEARCH_DATABASE_URL`·`GOODMORNING_READER_DATABASE_URL` 또는 각 역할의 로컬 키만 사용합니다. 관리자 환경변수로 자동 대체하지 않습니다. 역할 이름·고권한 플래그·객체 소유 여부를 검사해 잘못된 연결은 거부합니다. 관리자 연결은 `GOODMORNING_ADMIN_DATABASE_URL`을 사용하고, 기존 `GOODMORNING_DATABASE_URL`은 유지보수용 호환 입력으로만 남깁니다.

서버 시작 시 스키마를 만들거나 권한을 다시 부여하지 않습니다. 오프라인 설치가 적용되었는지만 확인합니다. 재시작 때문에 중단된 작업 상태 정리에는 입력값과 동적 SQL이 없는 `gm_recover_jobs()` 함수를 사용합니다. API 역할만 실행할 수 있고, 작업 실패 처리·오래된 검색 결과 정리 외 작업이나 결과 반환을 하지 않습니다.

## 회원별 행 단위 보안(RLS)

다음 12개 테이블에 `ENABLE` 및 `FORCE ROW LEVEL SECURITY`를 적용합니다.

`ownership`, `assets`, `jobs`, `diaries`, `notebook_pages`, `notebook_files`, `asset_trash`, `goods_searches`, `asset_product_links`, `user_notebooks`, `diary_pages`, `diary_page_items`.

- 서버가 검증한 세션의 소유자를 `ContextVar`로 전달하고, 연결을 빌릴 때마다 트랜잭션 한정 `set_config(..., true)`로 설정합니다. 소유자가 없으면 개인 자료 접근은 기본 거부됩니다.
- 사진/스티커 작업과 검색 백그라운드 스레드에도 작업 소유자를 명시적으로 전달합니다. 롤백·연결 재사용 후 다른 요청으로 권한이 남지 않는지 검증합니다.
- 기본 샘플 에셋 3개만 전체 사용자에게 읽기를 허용합니다. 샘플 수정 권한은 공개하지 않습니다.
- 기존 자료 중 암묵적으로 로컬 소유였던 항목은 소유권 행을 추가해 명확히 연결합니다. 기존 소유권을 덮어쓰지 않습니다.
- 관리자 조회 역할에는 명시적인 전체 행 읽기 정책을 두고 로컬 관리자 라우트로만 사용합니다. 이 역할은 회원용 API 연결과 분리됩니다.
- 인증을 위해 계정을 찾는 `auth_identities`·`account_profiles`·`account_sessions`·`oauth_attempts`와 사용자 바인딩은 인증 서버가 접근해야 하므로 회원별 RLS 적용 대상과 구분합니다. 검색·조회 역할에는 인증 테이블 권한을 주지 않습니다.

이 RLS는 소유자 조건 누락에 대한 추가 방어입니다. API 서버 자체가 완전히 장악되어 공격자가 임의 SQL과 소유자 컨텍스트를 설정할 수 있는 경우까지 차단하는 독립된 인증 체계는 아닙니다. 파라미터화된 쿼리와 서버 인증 검사를 함께 유지해야 합니다.

## 검색·관리자 경계

- 검색 HTTP 인증은 `data/search-service.key`를 사용합니다. PC 소유자용 `access.key`를 검색 서버에서 받지 않으므로 검색용 키가 API 관리자 권한으로 연결되지 않습니다.
- 크롤러 하위 프로세스에는 OS 실행에 필요한 환경변수만 전달하고 DB·OAuth·쇼핑 API 비밀 환경변수는 상속하지 않습니다.
- `/api/admin/*`는 소유자 인증에 더해 로컬 주소, Cloudflare 경유 여부, 요청 출처를 검사합니다. 공개 터널에서는 소유자 키가 있어도 DB 조회를 거부합니다.
- DB 포트와 검색 서버는 loopback에 바인딩합니다. 기존 외부 이미지의 HTTPS·호스트·포트·크기 제한, 상품 URL 제한, 사진 크기 제한, 고정 모델 리비전을 유지합니다.
- 기존 읽기 전용 관리자 쿼리는 1개 문장, 읽기 전용 트랜잭션, 5초 제한, 300행 제한을 유지합니다. 새 실행 DB 역할에는 30초 쿼리 제한과 60초 유휴 트랜잭션 제한을 설정합니다.
- 비밀 파일 스캐너는 이제 `data/*.key` 전체를 확인하므로 새 DB/서비스 키도 staged 코드와 배포 파일 누출 검사에 포함됩니다.

## 적용·검증 절차

1. 이미지·검색 작업이 없는지 확인하고 두 API 서버를 멈춥니다. 터널은 유지할 수 있습니다.
2. `python scripts/harden_database.py`가 DB 백업을 만들고 임시 DB에 실제 복원한 뒤 원본과 행 내용 지문을 비교합니다.
3. 한 트랜잭션으로 역할·권한·RLS를 적용하고, 기존 테이블 내용과 소유권 보존을 검사합니다. 임시 복원 DB는 확인 뒤 제거합니다. 백업은 로컬에 남습니다.
4. `scripts/start.ps1`로 서버를 시작하고 역할 플래그·RLS·로컬/외부 엔드포인트를 확인합니다.
5. CI에서 격리 DB를 사용한 권한 거부·회원 간 접근 차단·세션 보안 검증과 웹 빌드/비밀 검사를 실행합니다. 테스트 역할도 고유한 임시 이름을 사용해 운영 역할 비밀번호를 바꾸지 않습니다.

신규 설치는 `scripts/setup-postgres.ps1`에서 같은 보안 설정을 적용합니다. 기존 설치에 다시 적용할 때도 서버를 먼저 멈춰야 합니다. 실패 시 서비스를 관리자 계정으로 되돌려 우회하지 말고 백업과 진단을 먼저 확인합니다.

## 이번 적용 결과와 남은 범위

- 2026-11-27: 운영 DB 백업 실제 복원 검증 성공. 마이그레이션 이력 테이블을 제외한 기존 29개 테이블 검사, 기존 소유권 보존, 암묵적 로컬 소유권 4건 추가. 실행 역할 3개와 FORCE RLS 12개 적용 확인.
- 격리 DB·인증·권한 검증 19개 통과. 기존 다이어리 소유자 2명의 페이지 수가 제한된 API 역할에서도 각각 보존됨을 확인. 외부 미인증 관리자 요청은 401이며, 소유자 자격이어도 외부 경유를 거부하는 조건은 격리 요청 테스트로 확인.
- 로컬 API·검색 서버 응답 및 모델 로드 확인. 검색 서버가 소유자용 키를 거부하고 전용 키만 받는 것 확인. 사진 생성·UI·실제 OAuth 로그인 왕복은 사용자 확인 대상으로 유지합니다.
- **OS 수준 격리는 아직 적용하지 않았습니다.** API·검색·크롤러는 동일 Windows 사용자 권한으로 실행되므로 프로세스가 완전히 장악되면 로컬 비밀 파일을 읽을 가능성이 남습니다. 다음 단계는 별도 OS 계정/컨테이너, 최소 파일 마운트, 네트워크 egress 제한입니다. 환경변수 제한이나 가상환경은 이를 대체하지 않습니다.
- 도메인 허용 목록만으로 DNS rebinding 등을 완전히 막는다고 보장하지 않습니다. 네트워크 수준의 내부망 접근 차단은 후속 범위입니다.
- 암호화된 외부 백업·정기 복원 훈련·회원 탈퇴·보관기간 정책·보안 이벤트 경보도 후속 범위입니다. 이번 로컬 백업에는 사용자 자료가 포함되므로 외부에 올리면 안 됩니다.

설계 근거: [PostgreSQL 17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [PostgreSQL 권한](https://www.postgresql.org/docs/17/sql-grant.html), [OWASP 프롬프트 인젝션 방어](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html).
